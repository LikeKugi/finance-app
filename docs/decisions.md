# Initial implementation decisions

- Start with a Rust workspace containing `finance-app`, `finance-ui`, and `finance-db`; add `finance-core` when domain types and exact monetary input are introduced. Add `finance-export` only when export functionality is implemented.
- Use `gpui-kit` (GPUI) for the native desktop window (replaced `eframe`/`egui`; no egui code remains) and `rusqlite` with bundled SQLite for the local database.
- Store the database and rolling logs under the operating-system user's application data/configuration directory. On Windows this resolves under `%APPDATA%\FinanceApp`.
- Migration V1 is immutable and contains the existing app-settings table. Migration V2 introduces banks, income/expense categories, and income/expense transactions. Migration V3 adds savings accounts. Migration V4 adds payment documents and card-to-savings links. Migration V5 adds optional opening and interest-accrual dates to savings accounts. Migration V6 adds optional card currency and income-to-card references. Migration V7 adds optional expense-to-card references and the expense rate-counting flag; existing expenses remain unlinked and not counted. Migration V8 adds the currency directory and removes fixed RUB/USD schema restrictions from income, expense, and payment-document currency fields while preserving their values and references. Migration V9 adds an optional savings currency reference; existing savings retain unknown (`NULL`) currency. Migration V10 adds an expense balance-applied marker, defaulting existing expenses to not applied so upgrading never retroactively changes card balances, and adds guards for applied-expense/card-type consistency. At startup, only an empty database or a database with a contiguous known migration history is eligible for automatic migration; non-empty unversioned, malformed, and newer histories are rejected without schema or data changes.
- Migration V11 adds an optional non-empty payment-card name, the `expense_places` directory with a required non-empty name and optional comment, and an optional restricted foreign-key reference from expenses. Existing cards and expenses keep `NULL` values; the migration does not assign places or change transaction data. These schema fields are not yet exposed by the UI or database CRUD API.
- Migration V12 adds the `transfers` journal: an ISO operation date, one of `top_up`/`transfer`/`withdrawal`, exactly one internally consistent source and destination link, a canonical decimal amount, an explicit RUB/USD currency, an optional comment, and a UTC `created_at` timestamp. Foreign keys restrict deletion of any card or savings account referenced by history. CHECK constraints and triggers reject self-transfers, credit cards, currency mismatches, and accounts with unknown currency; changing a referenced card's type or any referenced account's currency is blocked. Indexes cover date, type, and all four reference columns. Upgrading from V11 uses the existing `VACUUM INTO` backup mechanism and preserves data.
- Transfers follow option A: top-up and cash withdrawal change only account balances and the transfer journal; no income or expense row is created, so «Анализ» stays transactional and the sum of balances may legitimately differ from the report total. This divergence is stated explicitly on the page. Transfers require the same explicitly configured currency on both accounts; cross-currency conversion is deferred because V8 stores only one current rate without history, rounding, or an application date. Credit cards are excluded because their `amount` is a credit limit, not user-owned money; debt repayment is not modeled. Inactive savings remain in history but are unavailable for new operations. Early withdrawal from a limited-term savings account is allowed with a visible warning. No cash wallet or initial balances are introduced. Transfer amounts use exact `Decimal` arithmetic with checked operations; insufficient funds abort the whole transaction and leave every balance unchanged. Editing or deleting a transfer reverses the previous two legs exactly before applying or removing the record.
- When upgrading a recognized older version, create an adjacent consistent backup via SQLite `VACUUM INTO` before applying pending migrations. Apply every pending schema change and its history rows in one transaction, and compare `PRAGMA data_version` after acquiring the write lock so a concurrent external update aborts the upgrade. V8 and V15 temporarily disable foreign-key enforcement during table rebuilds, remove and recreate affected triggers in the same transaction, check every reference before commit, and restore enforcement. The backup filename includes the target schema version and a timestamp.
- Transaction amounts are positive `rust_decimal::Decimal` values stored as canonical decimal `TEXT`, never calculated through SQLite floating-point aggregation. RUB and USD totals remain separate when no exchange rate is configured.
- Migration V15 rebuilds `savings` to allow the additional `interest_destination` code `other`, copying all existing values and preserving its indexes, foreign-key references, and dependent triggers. Existing `reinvest` and `withdraw` values are unchanged.
- Savings amounts, rates, and thresholds are stored as canonical decimal `TEXT`; term and interest-destination values use the explicit codes `limited`/`unlimited` and `reinvest`/`withdraw`/`other`. The `other` code (UI label «Другое») is classification only: it has no free-text explanation and does not change money movement or interest calculations. Optional opening and interest-accrual dates use ISO `YYYY-MM-DD` text and remain unknown (`NULL`) unless entered. Savings currency is optional and explicitly selected as RUB or USD; pre-existing accounts retain unknown currency until the user specifies it. A savings account references an existing bank with deletion restricted while it is in use.
- Savings CRUD and bank/status/currency/destination/text filtering are implemented. The interest-payout dialog updates the reference accrual date and existing destination; when the user chooses to create income, its editable default is the current balance multiplied by the selected rate and divided by 100, with no date factor and `MidpointAwayFromZero` rounding to two decimal places. The higher-rate checkbox is an explicit user confirmation only and changes the default only while the amount remains automatic; a manual amount is retained. The form creates an ordinary income with an active income category and a user-selected recipient: a matching debit card uses existing atomic income balance logic, no card changes no balance, and the current savings account creates both a separate ordinary income and a `top_up` transfer. The income and transfer use the selected income date and are atomic with the reference date/destination update, but later edits to the income do not synchronize the transfer. A savings recipient requires an explicitly configured matching currency; the app never assigns one automatically. Without the income checkbox, balances and financial journals remain unchanged. These values represent user-directed postings, not a bank-calculated or verified interest payment. Actual accrual estimates, yield projections, balance history, bank-specific rules, and verification of qualifying card spending remain deferred.
- Payment documents store supported system codes exactly as `VISA`, `MasterCard`, and `MIR`. Debit-card `amount` means current balance; credit-card `amount` means credit limit, never user-owned funds. Card currency is optional and explicitly selected as RUB or USD in the current UI; pre-existing cards retain unknown currency until the user specifies it. The V8 database field accepts any currency registered in the currency directory, while the domain form currently exposes only RUB and USD. Currency filters on savings and payment cards match only the selected currency; `Все` also includes records whose currency is unknown (`NULL`). A debit-card balance may be zero.
- An income may optionally credit a debit card of the same explicitly specified currency; no conversion is performed. Saving, editing, moving or deleting an income adjusts the balance and the income atomically, rejecting overflow or a negative resulting balance. Changing a linked card's currency or type and deleting it is prohibited. Direct manual changes to a card balance remain possible; if they leave insufficient funds, a later reversal of an income fails without modifying data. An expense may optionally reference a debit or credit card only when the card's explicitly specified currency matches the expense. New expenses linked to debit cards subtract their exact amount from the current balance atomically; editing, moving, unlinking, or deleting an applied expense adjusts or restores the debit balance in the same transaction. Insufficient balance and arithmetic overflow reject the whole operation. Credit-card limits are never changed by expenses. Expenses present before migration V10 are not retroactively deducted; their first save with a debit card applies the current amount, and deleting an un-applied historical expense has no balance effect. A debit card with applied expenses cannot be changed to a credit card, including by direct SQL; deleting any referenced card or changing its currency remains prohibited.
- Card links are allowed only between a payment document and savings accounts at the same bank. SQLite triggers protect link inserts/updates, bank changes, and disabling rate influence; replacing a card's linked savings is transactional. Turning off rate influence removes the card's links in that same save.
- A linked card and monthly spend threshold describe a conditional rate opportunity only. An expense can be explicitly marked as counting toward deposit-rate conditions only when its referenced card has rate influence enabled; this records the user's intent, but does not calculate the threshold, prove eligibility, or calculate yield. The schema intentionally does not store a card number or last digits.
- Analysis uses inclusive optional date bounds and supports all transactions, income only, or expenses only. Category totals and shares are grouped by transaction kind, category ID, and currency; RUB and USD remain separate, with no currency conversion. The report reads both transaction tables in a single read-only SQLite snapshot. Interest estimates, forecasts, and special-category criteria remain deferred until their semantics and data sources are agreed.
- V8 initializes RUB as the primary currency and USD without an assumed rate. Currency codes are three uppercase ASCII letters. A non-primary rate means the number of primary-currency units per one unit of the listed currency and must have an ISO date; a missing rate remains unknown. User-entered rates allow at most 12 decimal places. Changing the primary currency requires its known rate and rebases all known rates in one transaction, rounded to 24 places using midpoint-to-even; unknown rates remain unknown, and transaction amounts are never converted or changed. The directories screen allows adding currencies, setting dated rates, selecting a known-rate currency as primary, and deleting only non-primary currencies unused by income, expense, or payment-document records. The transaction domain/API and UI remain limited to RUB/USD; additional directory currencies cannot yet be used in transaction forms.
- Currency exchange rates are displayed with five decimal places using midpoint-to-even rounding. If rounding would turn a nonzero rate into zero, the directory displays `<0.00001` (or `>-0.00001` for a negative value); otherwise, it marks a displayed rate when rounding changes its numeric value. Stored rates and the edit form retain their full precision.
- The start page `Главная` is the first tab and is opened on launch instead of Income. Instead of navigation-only quick actions, it centers one vertical form titled `Добавление` (`quick_forms.rs`) with a segmented `Доход / Расход` selector: exactly one type is active, and switching reloads type-specific categories and cards. The amount uses the same `parse_amount_expression` as the transaction dialogs; the form has full-width Small selects for currency, category, card (`Зачислить на карту` for income, `Списать с карты` for expenses), and expense place (expenses only). Records use the current date (shown near the amount), an empty comment, and `affects_deposit_rate = false`; transaction semantics and balance effects are identical to creating the record on its own page. Creating a transfer is only available on the Transfers page; the home page no longer reads accounts to check transfer availability. No amounts, balances, or financial calculations are shown.
- The settings screen stores `system`, `light`, or `dark` in the existing `app_settings.theme` key; a missing value defaults to the system preference and the previous `dark` value remains compatible. Data export is a complete SQLite `.db` snapshot made through the SQLite backup API and never overwrites an existing destination. Import accepts a recognized supported schema, validates integrity and foreign keys, migrates a staged copy to the current schema, and requires confirmation; the app closes its database connection before replacing the live file and creates a separate consistent backup first. CSV, XLSX, and SQL text export/import are not part of this feature.
- The `Следующий платёж` dialog updates a credit card's date and optional amount atomically with an optional expense. The expense date and amount are initialized from the payment's original values and can be edited independently; currency is initialized from the credit card if known. Missing expense values require explicit input. New expenses default to `Без карты`, so no balance is changed unless a card is explicitly selected; normal expense rules then apply.
- Informational text that users may need to reuse is rendered as `gpui_base::SelectableText` through `crates/ui/src/gpui/selectable.rs`: page errors, warnings, footnotes, balance summaries, home-page descriptions, the settings description and version, the full transaction comment in its dialog, and the visible text of data cells in every `DataTable`. Such text takes part in the window-scoped selection layer mounted by the window root, so drag selection, double-click word selection, triple-click line selection, and `Ctrl+C`/`Cmd+C` copying work without extra per-screen handlers. Table cells use stable database row ids in their element ids, so sorting, filtering, and virtual scrolling do not move the selection anchor. Text inside buttons, selects, and tooltips stays plain, and action columns remain non-selectable. A comment cell copies its visible preview; the full comment remains selectable in the existing dialog. Selection start/length is not persisted, is not written to logs, and does not alter stored data.
- Card option labels are built by one helper in `crates/ui/src/gpui/helpers.rs` as `Название - Банк - Система (Тип; Валюта)`; cards without a name start with the bank name and cards without a currency use `валюта не указана`. The card id is no longer part of the label, as requested, so two otherwise identical cards produce the same visible option; selection by label therefore identifies the first matching card.
- Expense place labels are built by one helper in `crates/ui/src/gpui/helpers.rs` as `Название (Комментарий)`; a place without a non-blank comment is labeled by its name alone. The technical id is no longer part of the label, as requested, and the same text is used for select options, tooltips, and the «Место покупки» cell of the prices table on the transaction, payment document, and prices screens. Places with identical labels are indistinguishable in a select, so selection by label resolves to the first matching place.
- Запуск главного окна в полноэкранном режиме управляется настройкой `app_settings.start_fullscreen` со значениями `true`/`false`; отсутствующая или некорректная запись означает оконный режим. Чекбокс на странице «Настройки» сохраняет значение сразу через существующий DB API, но не меняет уже открытое окно: режим применяется при следующем запуске. Схема базы и миграции не меняются.
- On the «Накопления» page the first two table columns are `Название` and `Банк`. This is a presentation-only change: no database schema or migration is affected. Saved column widths move to the `table_columns.savings.v3` setting; widths stored under `table_columns.savings.v2` and the older `table_columns.savings` key are remapped so each column keeps its previous width.
- The «Накопления» table adds a fixed 40 pt `Inspector` action inside the «Выплата процентов» group. Saved widths use `table_columns.savings.v4`; existing `v3` widths are carried forward with the new action column inserted, while `v2` and legacy widths retain their earlier column-order remapping. The accrual date, destination, optional income, and optional savings `top_up` use existing entities and tables; no schema migration is required.
