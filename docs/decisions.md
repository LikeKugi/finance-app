# Initial implementation decisions

- Start with a Rust workspace containing `finance-app`, `finance-ui`, and `finance-db`; add `finance-core` when domain types and exact monetary input are introduced. Add `finance-export` only when export functionality is implemented.
- Use `eframe` for the native desktop window and `rusqlite` with bundled SQLite for the local database.
- Store the database and rolling logs under the operating-system user's application data/configuration directory. On Windows this resolves under `%APPDATA%\FinanceApp`.
- Migration V1 is immutable and contains the existing app-settings table. Migration V2 introduces banks, income/expense categories, and income/expense transactions. Migration V3 adds savings accounts. Migration V4 adds payment documents and card-to-savings links; upgrading an existing versioned database first creates a consistent adjacent SQLite backup via `VACUUM INTO`.
- Transaction amounts are positive `rust_decimal::Decimal` values stored as canonical decimal `TEXT`, never calculated through SQLite floating-point aggregation. RUB and USD totals remain separate when no exchange rate is configured.
- Savings amounts, rates, and thresholds are stored as canonical decimal `TEXT`; term and interest-destination values use the explicit codes `limited`/`unlimited` and `reinvest`/`withdraw`. A savings account references an existing bank with deletion restricted while it is in use.
- Savings CRUD and bank/status/text filtering are implemented, but accrued interest and potential income remain deferred: the current model has no opening date, balance history, accrual schedule, savings currency, or verified source for qualifying card spending. The higher rate is conditional and is not reported as achieved yield.
- Payment documents store supported system codes exactly as `VISA`, `MasterCard`, and `MIR`. Debit-card `amount` means current balance; credit-card `amount` means credit limit, never user-owned funds. No currency is assigned to these amounts because the current model does not define one.
- Card links are allowed only between a payment document and savings accounts at the same bank. SQLite triggers protect link inserts/updates, bank changes, and disabling rate influence; replacing a card's linked savings is transactional. Turning off rate influence removes the card's links in that same save.
- A linked card and monthly spend threshold describe a conditional rate opportunity only. Spending is not attached to cards, so the app does not claim that a threshold is satisfied or calculate yield from it. The schema intentionally does not store a card number or last digits.
- Analysis formulas, cross-currency totals, and export behavior remain deferred until their semantics and data sources are agreed and implemented.
