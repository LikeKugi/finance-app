# Initial implementation decisions

- Start with a Rust workspace containing `finance-app`, `finance-ui`, and `finance-db`; add `finance-core` when domain types and exact monetary input are introduced. Add `finance-export` only when export functionality is implemented.
- Use `eframe` for the native desktop window and `rusqlite` with bundled SQLite for the local database.
- Store the database and rolling logs under the operating-system user's application data/configuration directory. On Windows this resolves under `%APPDATA%\FinanceApp`.
- Migration V1 is immutable and contains the existing app-settings table. Migration V2 introduces banks, income/expense categories, and income/expense transactions. Migration V3 adds savings accounts. Migration V4 adds payment documents and card-to-savings links. Migration V5 adds optional opening and interest-accrual dates to savings accounts. Migration V6 adds optional card currency and income-to-card references. Migration V7 adds optional expense-to-card references and the expense rate-counting flag; existing expenses remain unlinked and not counted. Migration V8 adds the currency directory and removes fixed RUB/USD schema restrictions from income, expense, and payment-document currency fields while preserving their values and references. At startup, only an empty database or a database with a contiguous known migration history is eligible for automatic migration; non-empty unversioned, malformed, and newer histories are rejected without schema or data changes.
- When upgrading a recognized older version, create an adjacent consistent backup via SQLite `VACUUM INTO` before applying pending migrations. Apply every pending schema change and its history rows in one transaction, and compare `PRAGMA data_version` after acquiring the write lock so a concurrent external update aborts the upgrade. V8 temporarily disables foreign-key enforcement only while rebuilding the three currency-bearing tables, then checks every reference before commit and restores enforcement. The backup filename includes the target schema version and a timestamp.
- Transaction amounts are positive `rust_decimal::Decimal` values stored as canonical decimal `TEXT`, never calculated through SQLite floating-point aggregation. RUB and USD totals remain separate when no exchange rate is configured.
- Savings amounts, rates, and thresholds are stored as canonical decimal `TEXT`; term and interest-destination values use the explicit codes `limited`/`unlimited` and `reinvest`/`withdraw`. Optional opening and interest-accrual dates use ISO `YYYY-MM-DD` text and remain unknown (`NULL`) unless entered. A savings account references an existing bank with deletion restricted while it is in use.
- Savings CRUD and bank/status/text filtering are implemented, and the optional dates are manually maintained reference values. Accrued-interest and potential-income calculations remain deferred: there is no balance history, accrual schedule, savings currency, bank-specific rule model, or verified source for qualifying card spending. The higher rate is conditional and is not reported as achieved yield; a recorded accrual date is not treated as proof of a calculated or bank-verified interest payment.
- Payment documents store supported system codes exactly as `VISA`, `MasterCard`, and `MIR`. Debit-card `amount` means current balance; credit-card `amount` means credit limit, never user-owned funds. Card currency is optional and explicitly selected as RUB or USD in the current UI; pre-existing cards retain unknown currency until the user specifies it. The V8 database field accepts any currency registered in the currency directory. A debit-card balance may be zero.
- An income may optionally credit a debit card of the same explicitly specified currency; no conversion is performed. Saving, editing, moving or deleting an income adjusts the balance and the income atomically, rejecting overflow or a negative resulting balance. Changing a linked card's currency or type and deleting it is prohibited. Direct manual changes to a card balance remain possible; if they leave insufficient funds, a later reversal of an income fails without modifying data. An expense may optionally reference a debit or credit card only when the card's explicitly specified currency matches the expense. Expenses do not change card balances; deleting a referenced card or changing its currency is prohibited.
- Card links are allowed only between a payment document and savings accounts at the same bank. SQLite triggers protect link inserts/updates, bank changes, and disabling rate influence; replacing a card's linked savings is transactional. Turning off rate influence removes the card's links in that same save.
- A linked card and monthly spend threshold describe a conditional rate opportunity only. An expense can be explicitly marked as counting toward deposit-rate conditions only when its referenced card has rate influence enabled; this records the user's intent, but does not calculate the threshold, prove eligibility, or calculate yield. The schema intentionally does not store a card number or last digits.
- Analysis uses inclusive optional date bounds and supports all transactions, income only, or expenses only. Category totals and shares are grouped by transaction kind, category ID, and currency; RUB and USD remain separate, with no currency conversion. The report reads both transaction tables in a single read-only SQLite snapshot. Interest estimates, forecasts, special-category criteria, and exports remain deferred until their semantics and data sources are agreed.
- V8 initializes RUB as the primary currency and USD without an assumed rate. Currency codes are three uppercase ASCII letters. A non-primary rate means the number of primary-currency units per one unit of the listed currency and must have an ISO date; a missing rate remains unknown. User-entered rates allow at most 12 decimal places. Changing the primary currency requires its known rate and rebases all known rates in one transaction, rounded to 24 places using midpoint-to-even; unknown rates remain unknown, and transaction amounts are never converted or changed. The directories screen allows adding currencies, setting dated rates, selecting a known-rate currency as primary, and deleting only non-primary currencies unused by income, expense, or payment-document records. The transaction domain/API and UI remain limited to RUB/USD; additional directory currencies cannot yet be used in transaction forms.
