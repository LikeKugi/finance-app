# Current Architecture and Implementation Status

This document describes the architecture and functionality present in the repository, rather than the target architecture in `AGENTS.md`. It is based on the current source, crate manifests, migrations, and `docs/decisions.md`; update it when those change materially.

## Workspace and crate responsibilities

The Cargo workspace currently contains four crates:

| Crate | Current responsibility |
|---|---|
| `finance-app` (`crates/app`) | Application entry point; resolves the user's configuration directory, initializes logging and SQLite, then starts the UI. |
| `finance-core` (`crates/core`) | Domain types, validation, exact decimal parsing and formatting, and transaction and analysis value types. Most implementation is currently in `src/lib.rs`. |
| `finance-db` (`crates/db`) | SQLite initialization, schema migrations, queries, persistence operations, and database-level validation. Most implementation is currently in `src/lib.rs`; migration SQL is under `migrations/`. |
| `finance-ui` (`crates/ui`) | Native `gpui-kit` application and Russian-language screens. The window shell and tabs are in `src/gpui/shell.rs`; each tab is a separate page in `src/gpui/`, and framework-independent helpers are in `src/gpui/support.rs`. |

There is no `finance-export` crate in the current workspace. CSV, XLSX, and SQL export functionality is not implemented.

The current dependency direction is:

```text
finance-app -> finance-ui, finance-db
finance-ui  -> finance-core, finance-db
finance-db  -> finance-core
finance-core -> (no application crates)
```

The UI currently calls `finance-db` operations directly; a separate application-service or ports layer is not present. This is a description of the current code, not a recommendation to expand that coupling.

## Application startup and data flow

`crates/app/src/main.rs` resolves the user's configuration directory through `directories::BaseDirs`, creates a `FinanceApp` subdirectory, initializes daily rolling logs, restores a confirmed staged database import after closing the UI connection, and opens `data.db` through `finance_db::initialize`. The log configuration retains up to seven files. On Windows the application data directory is `%APPDATA%\FinanceApp`; other platforms use their standard configuration directory.

The initialized SQLite connection and database path are passed to `finance_ui::run`. The UI renders the module screens and calls database functions to load, validate, and persist user changes. SQLite is bundled through `rusqlite`, so normal application use does not depend on a separately installed SQLite server or network access.

## Persistence, migrations, and exact values

The database crate embeds the migration SQL files from `crates/db/migrations/` and applies versions V1 through V16. On a genuinely new database, the initial migration transaction also inserts the default income and expense category trees; recognized existing databases are not seeded or reseeded during upgrades. Initialization enables SQLite foreign keys on the connection and sets a five-second busy timeout. An empty database or a database with a recognized, contiguous migration history can be initialized or upgraded; an unrecognized, malformed, or newer schema is rejected without replacing the database.

Before upgrading a recognized older schema, the application creates an adjacent consistent backup using SQLite facilities (`VACUUM INTO`, as recorded in `docs/decisions.md`). Pending migrations and migration-history updates are applied atomically. Do not edit an applied migration; add a new version instead.

V11 adds nullable names to payment cards, an `expense_places` table with required names and nullable comments, and a nullable `expenses.expense_place_id` foreign key that restricts deletion of referenced places. Existing cards may remain unnamed, while card names are supported by the domain model, database CRUD API, and payment-card form. Expense places have domain and database CRUD support, are managed in the directories screen, and can be selected on expense forms, displayed in the expense table, and used as a list filter; existing expenses without a place remain valid.

V14 adds `prices`, storing positive exact-decimal amounts as canonical text, RUB/USD currency codes, ISO dates, and a required `expense_places` reference with restricted deletion. The directories screen includes a price section with CRUD, inclusive currency/place/date filters, sortable columns, and persisted resizable widths (except actions). The price form uses a DatePicker for the date, offers suggestions from previously saved product names while typing, and shows place-name options with tooltips containing the place id and its comment.

V15 rebuilds `savings` to allow `interest_destination = 'other'`, preserving existing records, card and transfer references, indexes, and dependent triggers. The saved code is displayed as «Другое» and is a classification only; it adds no explanation field or financial behavior.

V16 adds `expense_categories.is_regular` with a default of `0` and a `0/1` CHECK. Existing and new expense categories start as non-regular; income categories are unchanged. `Category.is_regular` is `Option<bool>` (`None` for income), and `save_category` rejects a flag for income categories. The flag is personal to a category: reports read it from each transaction's own category without inheriting it from ancestors, so enabling or disabling it changes the whole report period. The directories form exposes the «Регулярные расходы» checkbox only for expense categories and the category table shows a copyable «Регулярная» column.

Financial amounts, rates, and thresholds are represented with `rust_decimal::Decimal` and stored as canonical decimal text rather than floating-point SQLite values. Income and expense operations support RUB and USD and are not converted implicitly. The currency directory and exchange-rate data exist in the database, but transaction forms and the transaction domain currently support only RUB and USD. Currency rates are user-provided; unknown rates remain unknown, and changing the primary currency does not rewrite transaction amounts.

## Implemented modules

- **Income and expenses:** create, edit, and delete with confirmation; category, date, currency, amount, and comment fields; optional expense-place selection; date/category/bank/payment-method/currency/text filtering and expense-place filtering; on Expenses, a `Регулярные расходы` filter with `Все` / `Регулярные` / `Не регулярные` that reads the current category flag without inheriting a parent's flag; and exact totals. The Expenses table has no `Регулярные` column; saved expense column widths containing that former column are migrated in memory by dropping its value. The payment-method filter is labelled `Способ получения` on Income and `Способ оплаты` on Expenses and offers `Все`, `Не по карте` (transactions with no linked payment document), and the available cards. Card options include every card when no bank is selected and only cards from the selected bank otherwise; changing the bank clears the card filter. Dates and date filters use inclusive bounds. Income and expense amounts are kept separate by currency, and the bank/card/place/regular filters do not change the date-range balance.
- **Directories:** bank and expense-place management, hierarchical income and expense categories, and activation/deactivation with protections for records in use. Expense-category create/edit forms include the «Регулярные расходы» checkbox; the table shows a separate «Регулярная» column. The flag is per category, is not inherited, and has no scheduled operations. Expense-place comments support multiline text and full-text viewing from the truncated table preview. The currency directory supports currency and dated-rate management, primary-currency selection, and safeguards against deleting a primary or used currency. Prices have a separate exact-decimal table with create/edit/delete confirmation, search by product name or place, currency, place, period-preset and inclusive date filters, sorting by all data columns, and adjustable persisted widths except for actions.
- **Savings:** create, edit, and delete; bank, currency, status, destination, and text filters; optional explicitly selected RUB/USD currency; rates and optional threshold values; term and interest destinations (`reinvest`, `withdraw`, `other`, displayed as «Капитализация», «На карту», and «Другое»); and optional opening/accrual reference dates. A compact 40 pt Inspector action in the interest-payout group opens a dialog to update the accrual date and destination, and optionally create an ordinary income with an active income category, date, exact amount, currency, recipient, and comment. Its editable default is current savings balance × the selected base or user-confirmed higher rate / 100, rounded to hundredths; dates are not part of the formula, and manually edited amounts are retained when the rate choice changes. A card recipient uses the existing debit-card balance logic; no-card income only adds the income record; the current savings recipient creates both an ordinary income and a separate `top_up` transfer using the income date. These records are atomic when created together but are not synchronized after later edits. A savings recipient requires a previously configured matching currency. The higher-rate checkbox records the user's confirmation only. `other` remains classification only. Amounts and rates are stored exactly; this user-selected default is not a bank-calculated or verified interest amount.
- **Payment documents:** create, edit, and delete with an optional card name; the name is the first table column and can remain blank for existing cards. Names are included in the card selectors on income and expense forms. Includes bank, currency, payment-system, and card-type filters; debit and credit fields; and savings links restricted to the same bank. Currency filters include currency-unspecified cards only when set to `Все`. Payment-system values are stored as `VISA`, `MasterCard`, and `MIR`. Debit-card amounts mean current balance; credit-card amounts mean the credit limit, not user-owned funds. Income can be linked to a debit card and adjusts its balance atomically. New expenses linked to debit cards subtract their amount and reverse that balance change when edited, moved, unlinked, or deleted; credit-card limits remain unchanged. V10 marks pre-existing expenses as not applied and does not retroactively deduct them.
- **Analysis:** inclusive date filtering and all/income-only/expense-only modes; category totals and shares by transaction type and currency; and separate RUB and USD results without implicit conversion. Expense and income sections and pie charts are displayed expense first, then income. Charts use `gpui-kit` `PieChart`; each chart opens its complete category legend in a scrollable dialog. Each transaction-type/currency group uses an independently sortable `DataTable` (category, operation count, amount, and share), with its total displayed below the table. Expense tables add a sortable «Регулярные» column showing «Да» or «Нет» from the current expense-category flag; they also add a second footer row «Регулярные» with the count, exact amount, and share of that currency's expense total. Income tables keep only the ordinary total and do not show the regular column. Above the charts, the report shows filtered income, expenses, and their balance for each currency present; this balance is the difference between transactions, not the user's cash balance. Reports read both transaction tables from a single read-only SQLite snapshot.

- **Detailed analysis:** the Analysis page has three top-level sections: «Общая аналитика» (the existing category/pie-chart report, unchanged), «Аналитика расходов», and «Аналитика доходов». The latter two have nested tabs: income supports overall, cards, banks, deposits, and currency; expenses additionally support expense places. Each nested report uses the income/expense page filters before grouping, groups by stable record ids plus currency, and shows exact per-currency totals and shares in a footer below the table. Expense reports also show a separate regular-expense subtotal by currency and operation count, calculated with the same applied filters except the regular/non-regular selector; this uses each transaction's own current category flag. Income reports do not show this subtotal. Rows with no linked card, bank, or place are grouped as «Не указано». Deposits read only the transfer journal: where savings is the destination for income and the source for expenses, including external top-ups, cash withdrawals, and transfers to another account; a transfer between two savings accounts contributes once to each side. Card links used for rate conditions are not movement of money. The deposit tab keeps unsupported filters visible but disabled and ignores them; the opposite card is filtered as source for top-ups and destination for withdrawals, while the bank filter applies to the savings account. The transfer-journal explanation appears in the footer below the table. Filters are stored separately for each nested tab and restored on return. Reports are read on a read-only SQLite snapshot in a background task with generation checks, and errors replace rather than annotate stale results. A sortable `DataTable` contains group, currency, operation count, amount, share, and a bar column; bars use separate scales per currency and are rendered in the same table rows so scrolling and sorting stay synchronized. Column widths use `table_columns.analytics_details.v1`.
- **Transfers:** a journal of top_up, transfer, and withdrawal operations that is the only source of balance history on this page. One atomic database operation adjusts the exact Decimal balances of up to two debit cards or savings accounts; editing and deleting reverse the previous legs. Top-up and withdrawal normally do not create income/expense transactions, so the balance summary may intentionally differ from the transactional Analysis report. The savings interest dialog is an explicit exception: it creates a separate ordinary income and `top_up` transfer atomically, without linking their later edits. Only RUB/RUB and USD/USD operations are supported; credit cards are excluded. The journal is filtered by inclusive date range, type, source, destination, currency, and text, and its column widths are stored under table_columns.transfers.v1.

The native UI exposes nine Russian-language tabs in this order: home, expenses, income, transfers, payment cards, savings, analysis, directories, and settings. `Главная` is the start page: it centers one vertical form titled `Добавление` that creates an income or an expense directly; an exclusive `Доход / Расход` segmented control switches the record type, and the small selects below it change with the selected type. It shows short descriptions of income, expenses, and directories and links to every page. It displays no totals or balances, performs no financial calculations, and loads directory data for the forms when the page is activated, not on every render. Creating a transfer is available on the Transfers page. Settings persist light, dark, or system theme preference and the start-fullscreen choice in the existing `app_settings` table (the fullscreen choice is applied only on the next launch). On Windows, the shell renders a compact Russian-language overlay with minimize, exit-fullscreen, and close buttons whenever the window is fullscreen, because the platform removes the native title bar and its controls in that mode; the overlay is absent in windowed mode. The settings page displays the `finance-app` package version in the page footer, and exports the whole database as a standalone SQLite backup using SQLite's backup API; imports validate integrity, foreign keys, and supported migration history, upgrade a staged copy, require confirmation, create a backup of the current database, and reopen the app with the imported data. Automated tests are primarily colocated in Rust source files, including the core, database, and UI crates, rather than a separate top-level `tests/` tree.

Informational text that users may need to reuse is selectable and copyable, including the visible text of data cells in every `DataTable`. Page errors, warnings, footnotes, balance summaries, home-page descriptions, the settings description and version, and the full transaction comment in its dialog are rendered through `crates/ui/src/gpui/selectable.rs`, which wraps `gpui_base::SelectableText`. Table cells use stable database row ids in their element ids, so sorting, filtering, and virtual scrolling do not move the selection anchor. The window root created by `gpui_kit::open_window` mounts the text-selection layer and the copy keybinding, so dragging, double-clicking a word, triple-clicking a line, and `Ctrl+C`/`Cmd+C` work without per-screen handlers. Buttons, selects, tooltips, and table action columns are not selectable; a comment cell copies its visible preview while the full comment stays selectable in its dialog.

## Performance check

An ignored release-mode database test (`analysis_slice_report_filters_100k_rows_within_one_second`) generated 100 016 synthetic income rows in a temporary SQLite database and measured one filtered detailed-analysis query at **69.7 ms** on macOS (darwin, Rust release profile, 2026-11-28). This measures the database read and exact aggregation only; GUI opening, Windows behavior, and the 1280×720 manual checks were not measured here.

## Deferred functionality and known limitations

- Actual bank-calculated interest accrual, yield projections, and automatic verification of card-spend thresholds are deferred. The payout dialog only offers an editable user-selected default from the current balance and selected rate; savings lack balance history and bank-specific accrual rules, and the higher-rate checkbox is not proof that a threshold was met.
- Analysis forecasts and currency conversion in reports are not implemented. RUB and USD are not combined into one amount. Regular expenses use the explicit category flag and do not imply a schedule, forecast, or verified card-spend condition.
- CSV, XLSX, and SQL dump export are not implemented; the settings screen currently imports and exports only complete SQLite `.db` backups.
- The database can store additional currencies and their rates, but transactions and transaction screens remain limited to RUB/USD.
- The current source provides a primary-currency selector in the directories screen. `README.md` still says that this selector is not surfaced in the UI; that statement is stale relative to `crates/ui/src/directories_page.rs`.
- Buttons, selects, tooltips, and table action columns cannot be selected with the mouse. A comment cell copies its visible preview; the full comment remains selectable after opening its dialog.
- This document does not assert that Windows packaging, installer behavior, or performance targets have been verified; those require their own platform-specific checks.
