# План: страница «Переводы»

Статус: план, реализация не начата. Описание опирается на фактическое состояние репозитория (миграции V1–V11, `crates/db/src/lib.rs`, `crates/core/src/lib.rs`, `crates/ui/src/gpui/shell.rs`, `docs/architecture.md`, `docs/decisions.md`).

## 1. Назначение

Страница управляет остатками карт и накоплений: пополнение счёта, перевод между своими счетами (карта ↔ карта, карта ↔ накопление, накопление ↔ накопление), снятие наличных. Журнал операций — единственный источник истории изменения остатков на этой странице.

## 2. Принятые решения (согласованы)

| Решение | Значение |
|---|---|
| Учёт в доходах/расходах | **Вариант A**: пополнение и снятие наличных не создают записей дохода/расхода, учитываются только в остатках и журнале переводов. Расхождение между суммой остатков и отчётом «Анализ» показывается пользователю явно (сноска на странице), а не скрывается |
| Доходы/расходы, привязанные к картам | Продолжают работать как сейчас (V6/V10): доход увеличивает баланс дебетовой карты, расход с `payment_document_balance_applied` уменьшает. Переводы этот механизм не подменяют |
| Валюта | Операция выполняется только при явно совпадающей валюте (`RUB↔RUB`, `USD↔USD`). Участники с `NULL`-валютой в операциях не участвуют. Межвалютные переводы не реализуются в этом срезе: в `currencies` один актуальный курс без истории (V8), нет правила округления и даты применения |
| Кредитные карты | Исключены как источник и получатель: `amount` кредитной карты — кредитный лимит, а не деньги пользователя. Пока нет модели задолженности, «погашение» не моделируется |
| Накопления с ограниченным сроком | Досрочная операция (`term_type='limited'` раньше `term_end_date`) допустима, но показывается предупреждение. Неактивные накопления (`is_active = 0`) недоступны для новых операций; исторические строки сохраняются |
| Отчёт «Анализ» | Остаётся транзакционным; переводы между своими счетами в доходы/расходы не попадают |
| Наличные и начальные остатки | «Кошелёк наличных» и начальные остатки не вводятся: снятие означает, что деньги покидают учитываемые счета |

Следствие варианта A: сумма остатков по картам и накоплениям может превышать сумму доходов (за счёт пополнений) и быть меньше (за счёт снятий). Это ожидаемое поведение, а не ошибка; оно должно быть явно описано в интерфейсе.

## 3. Модель данных: миграция V12

Файл `crates/db/migrations/V12__transfers.sql`, регистрация в `MIGRATIONS` (`crates/db/src/lib.rs`). Применённые миграции не изменяются.

```text
transfers
  id                              INTEGER PRIMARY KEY
  operation_date                  TEXT NOT NULL CHECK (длина 10, ISO-дата)
  operation_type                  TEXT NOT NULL CHECK IN ('top_up','transfer','withdrawal')
  source_kind                     TEXT NOT NULL CHECK IN ('external','card','savings')
  source_payment_document_id      INTEGER NULL REFERENCES payment_documents(id) ON DELETE RESTRICT
  source_savings_id               INTEGER NULL REFERENCES savings(id) ON DELETE RESTRICT
  destination_kind                TEXT NOT NULL CHECK IN ('cash','card','savings')
  destination_payment_document_id INTEGER NULL REFERENCES payment_documents(id) ON DELETE RESTRICT
  destination_savings_id          INTEGER NULL REFERENCES savings(id) ON DELETE RESTRICT
  amount                          TEXT NOT NULL — CHECK как у денежных полей V3/V4 (цифры, точка, непусто, > 0)
  currency                        TEXT NOT NULL CHECK IN ('RUB','USD')
  comment                         TEXT NULL
  created_at                      TEXT NOT NULL — UTC, техническая метка создания записи
```

Ограничения уровня БД:

- CHECK: ровно одна ссылка «откуда» и ровно одна «куда», согласованная с `*_kind`;
- CHECK: `top_up ⇒ source_kind='external'`, получатель — карта или накопление;
- CHECK: `transfer ⇒` оба участника внутренние и это разные счета (запрет перевода «на себя»);
- CHECK: `withdrawal ⇒ destination_kind='cash'`, источник — карта или накопление;
- внешние ключи — только `ON DELETE RESTRICT`: удаление карты/накопления с историей переводов запрещено.

Триггеры (защита от обхода прикладного слоя):

- карта-источник и карта-получатель — только `card_type='debit'`;
- валюта карты/накопления совпадает с валютой операции (на `INSERT` и `UPDATE`);
- запрет смены `card_type` на `credit` и смены валюты у карты/накопления, на которые есть ссылки из `transfers` (аналог `payment_documents_preserve_debit_for_applied_expenses`);
- неотрицательность остатков уже обеспечена CHECK-ограничениями самих таблиц — страховка даже при прямом SQL.

Индексы: по `operation_date`, по всем четырём ссылочным колонкам, по `operation_type`. Резервная копия перед обновлением схемы создаётся существующим механизмом (`VACUUM INTO`), изменений не требует.

## 4. `crates/core`

- `enum TransferOperationType { TopUp, Transfer, Withdrawal }`: коды `top_up`/`transfer`/`withdrawal`, русские подписи, `FromStr` (паттерн `PaymentCardType`, `PaymentSystem`).
- `enum TransferEndpoint { External, Cash, Card(i64), Savings(i64) }` с явным отображением в SQL-столбцы.
- `struct TransferRecord` (с `id`) и `struct TransferDetails` + `validate()` (паттерн `SavingsDetails::validate`).
- Валидация: сумма > 0; валюта обеих сторон явно задана и совпадает; источник ≠ получатель; кредитная карта запрещена; накопление активно; длина комментария по существующим правилам.
- Расчёт остатка — только `Decimal` с `checked_add`/`checked_sub` и проверкой обратного преобразования (как в `adjust_card_balance`), без `f32`/`f64`.
- Новые значения `DomainError`: несовпадение валют, совпадение источника и получателя, кредитная карта в операции, валюта счёта не указана, неактивное накопление.

## 5. `crates/db`

- `save_transfer(&Connection, id: Option<i64>, &TransferDetails) -> Result<i64, DbError>`: одна транзакция `Immediate`; проверка обоих участников; точное списание и зачисление; при редактировании — сначала сторно старой операции, затем применение новой.
- `delete_transfer(&Connection, id) -> Result<(), DbError>`: сторно обеих ног атомарно.
- `list_transfers_filtered(&Connection, date_from, date_to, operation_type, source, destination, currency, search)`: включённые границы дат (семантика как на доходах/расходах), один запрос, без N+1.
- Обобщить `adjust_card_balance` или добавить `adjust_savings_balance` для накоплений.
- Новые ошибки: `InsufficientFunds` (расширить `InsufficientCardBalance` или добавить отдельный), `TransferOverflow`, `TransferCurrencyMismatch`, `TransferCreditCardForbidden`, `TransferSameAccount`, `TransferAccountInUse`, `TransferSavingsInactive`.

- Фильтры по рекомендованному шаблону: `Период (С/По)`, `Тип операции`, `Источник`, `Назначение`, `Валюта`, `Поиск`; `Применить` и `Сбросить фильтры` справа в последней строке, `×` у каждого заполненного фильтра; условия объединяются через И; пустое состояние; `Обновить` не сбрасывает фильтры.
- Форма — модальный `Dialog` 800 pt по `docs/form-guidelines.md`: заголовок «Новый перевод» / «Изменение перевода»; поля «Дата», «Тип операции», «Откуда», «Куда», «Сумма», «Валюта», «Комментарий»; зависимые поля переключаются по типу операции; кнопки строго `Сохранить` и `Отмена` внизу справа; ошибки рядом с полями; при ошибке сохранения форма остаётся открытой и сохраняет ввод.
- Удаление — с подтверждением, где указаны дата, сумма и направление. Действия без выбранной записи заблокированы. Stack trace пользователю не показывается.
- Предупреждения в форме: пополнение — «запись дохода не создаётся»; снятие — «деньги выводятся из учёта остатков»; досрочное изъятие со срочного вклада — отдельное предупреждение.
- Без обращений к БД на каждом кадре; перезагрузка только по действию пользователя.

## 7. Тесты

**core**

- Decimal-арифметика и границы; переполнение;
- разбор и обратное преобразование кодов операций и сторон;
- валидация: нулевая сумма, несовпадение валют, `NULL`-валюта, источник = получатель, кредитная карта, неактивное накопление.

**db** (интеграционные, временная БД)

- V12 применяется на пустой БД; обновление с V11 проходит с резервной копией и сохраняет данные;
- пополнение, перевод и снятие меняют ровно две ноги остатков;
- при недостаточности средств операция отклоняется целиком, остатки не изменяются (rollback);
- редактирование и удаление сторнируют предыдущее изменение точно, без потери точности decimal-строк;
- прямой SQL-обход отклоняется триггерами: кредитная карта, несовпадение валюты, ссылка на себя;
- удаление карты/накопления с историей переводов запрещено (FK RESTRICT);
- смена типа карты на кредитную и смена валюты у связанной записи запрещены;
- для `transfer` сумма остатков консервативна; для `top_up`/`withdrawal` расхождение ожидаемо и покрыто тестом.

**ui**

- дефолты новой формы и отличие формы редактирования (паттерн существующего теста `new_form_has_expected_defaults_and_differs_after_edit` в `crates/ui/src/gpui/savings.rs`).

## 10. Ограничения, не входящие в этот план

- Межвалютные переводы (нужна история курсов и правило округления).
- Учёт наличных как отдельного счёта и начальные остатки.
- Задолженность по кредитной карте и операция «погашение».
- Windows-сборка, установщик и измерения производительности — отдельные проверки, этой задачей не покрываются.
- Экспорт переводов появится вместе с общим экспортом; до этого они попадают только в полный снимок БД.
