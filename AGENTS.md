# AGENTS.md

## Назначение

Этот файл задаёт правила работы AI-агентов и разработчиков над **FinanceApp** — локальным настольным приложением для управления личными и семейными финансами.

Целевая платформа: **Windows 10/11 x64**. Язык реализации: **Rust**. Данные хранятся в локальной **SQLite**.

Применяй правила ко всему репозиторию. Учитывай дополнительные `AGENTS.md` во вложенных каталогах, если они существуют.

**Работай в пределах текущего задания.** Запрос на подготовку документации не означает разрешение начинать реализацию приложения, менять архитектуру или выполнять миграции пользовательской базы.

## 1. Источники требований и разрешение противоречий

Источники требований:

1. Текущее задание пользователя и явно согласованные изменения.
2. `prompt.md` — основное техническое задание.
3. Этот `AGENTS.md` — инженерные правила и порядок выполнения работ.
4. `example.md` — дополнительные материалы: ER-модель, сценарии, примеры миграций, структура проекта и макеты.

Если файлы требований отсутствуют в репозитории, не утверждай, что они найдены или прочитаны. Используй предоставленные материалы и сообщай о недостающих источниках, когда это влияет на задачу.

При противоречии:

- обязательные требования ТЗ имеют приоритет над иллюстративными примерами;
- не меняй финансовую семантику без согласования;
- фиксируй существенные решения и допущения в `docs/decisions.md`;
- при неоднозначности продолжай независимые части работы, а спорную часть изолируй и сформулируй конкретный вопрос.

Примеры из `example.md` **не являются готовой production-реализацией**. В частности, нельзя переносить без исправления:

- хранение денег в `REAL`;
- подавление ошибок разбора через `unwrap_or_default()` и `.ok()`;
- копирование открытой SQLite-базы через обычный `std::fs::copy`;
- SQL-экспорт, содержащий только `INSERT` без схемы;
- проверку одного банка только при `INSERT` связи;
- автоматическую сериализацию `MasterCard` в несовместимое с БД значение `MASTERCARD`;
- жёстко заданную версию схемы в манифесте резервной копии.

## 2. Обязательные ограничения

- Приложение работает локально и не требует внешнего сервера.
- Основные функции доступны без подключения к интернету.
- Не использовать Docker, контейнеризацию и виртуализацию как условие запуска или установки.
- Основная СУБД — SQLite. Не добавлять PostgreSQL, сервер БД или облачное хранилище.
- Интерфейс должен быть нативным, русскоязычным, табличным.
- Не добавлять WebView, Tauri или браузерный frontend без отдельного согласования.
- Минимальное поддерживаемое разрешение — **1280×720**.
- Пользовательские данные должны сохраняться между запусками.
- Удаление записей требует подтверждения.
- Ошибки не должны приводить к незаметной потере, обнулению или пересозданию данных.
- Открытие модулей и фильтрация должны укладываться в **1 секунду на наборе до 100 000 записей** в согласованном тестовом окружении.

Сетевой доступ для получения зависимостей во время разработки не означает, что приложение может требовать сеть во время обычной работы.

## 3. Технологический стек

### 3.1. Если проект уже существует

Сначала изучи `Cargo.toml`, `Cargo.lock`, исходный код и принятые архитектурные решения.

Не заменяй работающий GUI-фреймворк, SQLite-драйвер или механизм миграций только ради соответствия примеру.

### 3.2. Если репозиторий создаётся с нуля

Предпочтительная согласованная связка:

| Назначение | Выбор |
|---|---|
| Язык | Rust stable |
| GUI | `egui` / `eframe` |
| База данных | SQLite через `rusqlite` |
| Поставка SQLite | `bundled`, без требования системного `sqlite3.exe` |
| Миграции | Один встроенный механизм; для `rusqlite` допустим `refinery`, как в дополнительных материалах |
| Денежные расчёты | `rust_decimal` |
| Даты | `chrono` |
| Сериализация | `serde`, `serde_json` |
| CSV | `csv` |
| XLSX | `rust_xlsxwriter` |
| ZIP | `zip`, если реализуется архивирование |
| Логирование | `tracing`, `tracing-subscriber` |
| Конфигурация | TOML и типизированная конфигурация |
| Установщик | NSIS или WiX |

Если выбран `sqlx` или `diesel`, используй соответствующий механизм миграций. Не подключай второй стек доступа к БД без обоснованной необходимости.

Правила зависимостей:

- выбирать совместимые версии, а не механически копировать версии из примеров;
- избегать конфликтующих зависимостей `libsqlite3-sys`;
- включать только необходимые features;
- хранить `Cargo.lock` в репозитории приложения;
- не обновлять зависимости, edition и MSRV попутно с несвязанной задачей;
- фиксировать используемый toolchain после проверки совместимости.

### Ответственность crates

**`core`**

- Доменные модели, перечисления, валидация.
- Денежные расчёты, аналитика, правила предметной области.
- Типизированные фильтры и контракты прикладных операций.
- Не зависит от GUI, SQLite и конкретных форматов экспорта.

**`db`**

- Соединения SQLite, миграции и репозитории.
- Транзакции, индексы, отображение SQL-значений в доменные типы.
- Согласованные снимки БД и инфраструктурные операции резервного копирования.

**`export`**

- CSV, XLSX, SQL-дампы, упаковка снимков БД.
- Работа через публичные API и согласованные наборы данных.
- Не дублирует правила расчётов из `core`.

**`ui`**

- Представление данных, формы, таблицы, диалоги.
- Состояние интерфейса и запуск прикладных операций.
- Не содержит SQL и самостоятельных финансовых формул.

**`app`**

- Точка входа.
- Конфигурация, логирование, сборка зависимостей.
- Инициализация БД, миграции, запуск интерфейса.

### Границы зависимостей

- `db` зависит от `core`.
- `ui` использует доменные типы и прикладные контракты.
- `export` использует `core`; доступ к БД допускается через выделенный публичный API снимков и чтения.
- `app` связывает реализации.
- Циклические зависимости запрещены.

Не называй библиотечный crate просто `core`, чтобы не создавать неоднозначность со стандартной библиотекой Rust. Для нового workspace используй имена пакетов:

```text
finance-core
finance-db
finance-export
finance-ui
finance-app
```

В Rust-коде соответствующие имена импортов: `finance_core`, `finance_db` и т. д.

Не вводи сложную универсальную архитектуру репозиториев, если задачу проще решить небольшими типизированными интерфейсами.

## 5. Порядок работы агента

Перед изменениями:

1. Прочитай действующие инструкции и требования к затрагиваемой функции.
2. Проверь структуру workspace и состояние рабочего дерева.
3. Найди существующие реализации, тесты и миграции.
4. Определи минимальный объём изменений.
5. Для нетривиальной задачи составь короткий план.
6. Выяви неоднозначности, влияющие на деньги, совместимость или сохранность данных.

Во время работы:

- делай небольшие, проверяемые изменения;
- сохраняй стиль и соглашения существующего проекта;
- не перезаписывай изменения пользователя;
- не выполняй несвязанные рефакторинги;
- не добавляй необязательные функции без запроса;
- не используй `todo!()`, `unimplemented!()` и фиктивные успешные ответы в завершённой функциональности;
- не выдавай демонстрационные данные за реальные пользовательские записи;
- не создавай коммиты без поручения;
- не выполняй разрушительные Git-команды без явного разрешения.

После изменений:

- запусти подходящие проверки;
- укажи, что проверено фактически;
- перечисли непроверенные платформы и сценарии;
- сообщи об оставшихся ограничениях;
- не объявляй весь проект завершённым после выполнения отдельного этапа.

## 6. Деньги, валюты и даты

### 6.1. Денежные значения

- Использовать `rust_decimal::Decimal` для денег, ставок, порогов и финансовых вычислений.
- Не использовать `f32` или `f64` в доменной финансовой логике.
- Не преобразовывать ввод сначала во float, а затем в `Decimal`.
- В SQLite хранить десятичные значения как канонический `TEXT`, если не согласована другая точная модель.
- Представление в минимальных денежных единицах через `INTEGER` допустимо только как осознанное решение с проверкой диапазонов и миграцией.
- Не смешивать способы хранения одного типа данных без явного преобразования.
- Формат хранения не должен зависеть от локали: десятичный разделитель — точка, разделители групп отсутствуют.
- Политику масштаба, округления и допустимых диапазонов определить централизованно и покрыть тестами.
- Переполнение и недопустимая точность должны возвращать ошибку, а не усекаться молча.

Для локализованного ввода можно поддержать запятую как десятичный разделитель, но неоднозначные форматы нужно отклонять.

Не применять SQL `SUM`, `AVG`, `CAST(... AS REAL)` и аналогичные операции к decimal-строкам, если результат теряет точность. Использовать точную агрегацию или согласованную модель хранения.

Сортировка денежных значений должна быть числовой. Лексикографическая сортировка `TEXT` недопустима.

### 6.2. Ошибки преобразования

При чтении БД:

- некорректный decimal — ошибка;
- неизвестное значение enum — ошибка;
- некорректная дата — ошибка;
- `Option<T>` отражает реальный `NULL`, а не неудачный разбор;
- повреждённая запись не должна превращаться в нулевую или исчезать из отчёта без сообщения.

Не использовать для таких преобразований:

```rust
value.parse().unwrap_or_default()
value.parse().ok()
```

Ошибку нужно снабдить техническим контекстом, не раскрывая лишние финансовые данные в логах.

### 6.3. Валюты

Поддерживаемые валюты операций:

```text
RUB
USD
```

- Исходная сумма и валюта сохраняются без изменения.
- Переключение валюты отображения не переписывает транзакции.
- Конвертация требует явного курса, направления котировки и даты его применения.
- Не использовать произвольный фиксированный курс или числа из макетов.
- Не подключать внешний сервис курсов без согласования.
- Для офлайн-режима допустим согласованный ручной курс.
- Один отчёт должен использовать согласованный снимок валютной политики.

Если курс не задан:

- показывать исходные суммы отдельно по валютам;
- явно сообщать о недоступности конвертации;
- не подменять результат нулём;
- не складывать RUB и USD в один итог.

В минимальной схеме валюта вкладов и карт отсутствует. Не распространяй валюту транзакций на эти сущности автоматически. Базовую валюту или расширение схемы необходимо зафиксировать отдельным решением.

### 6.4. Даты и время

- Дата финансовой операции — `chrono::NaiveDate`.
- Формат хранения даты — `YYYY-MM-DD`.
- Пользовательский формат отображения может быть русскоязычным.
- Границы выбранного периода должны иметь явно определённую семантику; для обычного фильтра дат использовать включённые начало и конец.
- Определение недели должно быть единым в UI, запросах и тестах.
- Технические временные метки хранить с однозначной временной зоной; предпочтительно UTC.
- Текущее время и дату передавать через тестируемую зависимость там, где они влияют на расчёты.
- Не зашивать даты из примеров в рабочую логику.

## 7. SQLite и миграции

### 7.1. Размещение данных

Основная база:

```text
%APPDATA%\FinanceApp\data.db
```

Логи:

```text
%APPDATA%\FinanceApp\logs
```

- Определять пользовательский каталог средствами ОС или подходящей библиотекой.
- Не хранить рабочую БД рядом с исполняемым файлом в `Program Files`.
- Не полагаться на текущий рабочий каталог.
- Не требовать прав администратора для обычной работы.
- В тестах использовать временные каталоги и отдельные БД.

### 7.2. Соединения и запросы

На каждом соединении:

- включать `PRAGMA foreign_keys = ON`;
- задавать согласованный `busy_timeout`;
- применять выбранные настройки журналирования и надёжности.

Дополнительно:

- использовать параметризованные запросы;
- не подставлять пользовательские значения в SQL через `format!`;
- динамические имена столбцов и направления сортировки выбирать только из whitelist;
- не передавать один `Connection` между потоками без корректной модели владения;
- не выполнять длительные запросы в цикле отрисовки GUI;
- составные операции выполнять транзакционно.

WAL допустим, но резервное копирование и восстановление должны корректно учитывать его особенности.

### 7.3. Миграции

Для `refinery` использовать каталог:

```text
crates/db/migrations/
```

Имена:

```text
V1__init_schema.sql
V2__savings.sql
V3__payment_documents.sql
```

Правила:

- использовать один источник миграций, без дублирования в нескольких каталогах;
- включать миграции в поставку приложения;
- на первом запуске автоматически создавать схему;
- не изменять уже применённые миграции;
- изменения схемы оформлять новой миграцией;
- версию схемы читать из фактической истории миграций;
- перед обновлением существующей БД создавать согласованную резервную копию;
- проверять обновление с поддерживаемых предыдущих версий;
- при ошибке миграции не удалять БД и не создавать пустую вместо неё;
- не выполнять автоматическое понижение схемы.

### 7.4. Минимальные таблицы

Обязательные сущности:

```text
banks
income_categories
expense_categories
incomes
expenses
savings
payment_documents
document_rate_links
```

Имена и поля должны соответствовать ТЗ либо иметь документированное отображение.

Не добавляй поля ради макета без доменной необходимости. Например, последние цифры карты на иллюстрации не означают требование хранить номер карты.

## 8. Инварианты предметной области

Проверки должны выполняться не только в UI, но и на уровне прикладных операций. Структурные ограничения дополнительно закреплять в БД, где это возможно.

### 8.1. Категории и банки

- Доход ссылается только на категорию доходов.
- Расход ссылается только на категорию расходов.
- Иерархия категорий не допускает ссылку на себя и циклы.
- Неактивные категории сохраняются в исторических записях.
- Неактивную категорию нельзя незаметно подставлять в новую операцию.
- Редактирование старой операции не должно требовать изменения её исторической категории без необходимости.
- Используемые категории и банки защищены от удаления.
- Не удалять финансовую историю каскадно.
- Каскадное удаление бизнес-данных допустимо только как отдельно согласованная операция с явным подтверждением последствий.

По умолчанию предпочитать запрет удаления или деактивацию.

### 8.2. Вклады и накопительные счета

Для `savings`:

- банк должен существовать;
- обязательные значения должны проходить доменную валидацию;
- `term_type = limited` требует `term_end_date`;
- `term_type = unlimited` требует `term_end_date = NULL`;
- допустимые `interest_destination`: `reinvest`, `withdraw`;
- согласованность пороговой ставки и пороговой суммы проверяется явно;
- статус активности не должен удалять историю или связи.

Не считать вклад закрытым только потому, что наступила дата окончания, если такое поведение отдельно не согласовано.

### 8.3. Платёжные документы

Точные значения платёжных систем в контракте хранения:

```text
VISA
MasterCard
MIR
```

Использовать явное отображение значений Rust enum, SQL и сериализации.

Для типов карт:

- `debit`: `due_date` и `grace_period_days` равны `NULL`;
- `credit`: дата платежа и льготный период заданы;
- льготный период неотрицателен;
- переход между типами должен приводить поля к согласованному состоянию.

Уточнить смысл `amount`:

- баланс дебетовой карты;
- лимит кредитной карты;
- задолженность или доступный остаток — только если это явно введено в модель.

**Кредитный лимит не является собственными денежными средствами пользователя.**

### 8.4. Связи карт и вкладов

Для `document_rate_links`:

- пара `(document_id, savings_id)` уникальна;
- карта и вклад должны принадлежать одному банку;
- создание и изменение набора связей выполняются транзакционно;
- удаление карты или вклада удаляет только соответствующие строки связей.

Проверка одного банка должна работать при:

1. Создании связи.
2. Изменении существующей связи.
3. Изменении банка карты.
4. Изменении банка вклада.

Для защиты от обхода прикладного слоя использовать ограничения и триггеры, покрывающие все соответствующие пути изменения.

Нельзя считать одного `BEFORE INSERT`-триггера достаточной защитой.

Если изменение банка делает существующие связи недействительными:

- либо блокировать изменение с понятным объяснением;
- либо предлагать явное подтверждённое удаление несовместимых связей.

При отключении `affects_deposit_rate` не оставлять активное влияние карты незаметно. Политику удаления или запрета сохранения связей определить явно.

## 9. Финансовые расчёты и неоднозначные требования

Формулы должны находиться в `core`, иметь единицы измерения, понятные входные параметры и тесты.

### 9.1. Проценты по вкладам

Не путать:

- оценку дохода;
- потенциальный доход при выполнении условий;
- фактически начисленные банком проценты.

Минимальная схема не содержит полной информации для банковского расчёта: даты открытия, истории остатков, периодичности капитализации и правил банка.

Поэтому:

- не называть приблизительную оценку фактически начисленным доходом;
- для оценки явно задавать период и модель расчёта;
- не выводить начало срока из `term_end_date`;
- не считать `reinvest` достаточным описанием периодичности капитализации;
- не создавать доходные операции автоматически без отдельного требования.

Для согласованной модели простых процентов возможна формула:

```text
income = principal × annual_rate / 100 × days / day_basis
```

Значения `days`, `day_basis`, правила округления и допущения должны быть определены до использования формулы.

### 9.2. Повышенная ставка

Наличие связанной карты не доказывает выполнение условий повышенной ставки.

В текущей модели расходы не привязаны к конкретной карте. Поэтому нельзя:

- считать все расходы пользователя расходами по связанной карте;
- автоматически признавать месячный порог выполненным;
- произвольно суммировать условия нескольких карт;
- без согласования выбирать логику «достаточно одной карты» или «нужны все карты».

До появления согласованного источника фактических трат показывать повышенную ставку как **условную возможность**, а не подтверждённую доходность.

### 9.3. Аналитика

До реализации итоговых формул определить:

- базу расчёта процентов;
- обработку режима «Все»;
- способ расчёта среднемесячной суммы;
- способ годового прогноза;
- обработку неполных месяцев;
- валютную политику;
- критерий «специальных категорий».

Не складывать доходы и расходы в неоднозначный общий объём. Не использовать чистый баланс как знаменатель процентов без утверждённой методики.

Пустой период и нулевой итог не должны приводить к делению на ноль.

Итоги рассчитывать из точных исходных значений, а не из уже округлённых строк отображения. Сумма отображаемых процентов может отличаться от 100% из-за округления — это не повод менять исходные суммы.

Не определять специальные категории по случайным названиям, подстрокам или цветам. Нужен явный признак, настройка либо документированное правило.

### 9.4. Показатели нижней панели

Формулы «На руках» и «Баланс» требуют отдельного определения.

Не допускается:

- считать кредитные лимиты наличными средствами;
- дважды учитывать одни деньги через транзакции и остатки счетов;
- придумывать начальные остатки;
- автоматически считать вклад расходом или его закрытие доходом.

Если модель начальных остатков и переводов отсутствует, обозначить ограничение и согласовать формулы.

## 11. Экспорт и резервное копирование

Обязательные форматы:

- полный снимок БД;
- SQL-дамп;
- CSV;
- XLSX.

ZIP и импорт — дополнительные функции, если они отдельно включены в задачу.

### 11.1. Общие требования

- Пользователь выбирает формат, область данных и каталог назначения.
- Для полного DB- и SQL-дампа ясно показывать, что экспортируется вся база.
- Не применять фильтр периода к полному дампу незаметно.
- Для табличного экспорта использовать согласованные фильтры модуля.
- Не применять фильтр периода к сущности, у которой нет подходящей даты, без определения его смысла.
- Показывать прогресс и итог операции.
- Не объявлять успех до завершения записи и закрытия файла.
- Не перезаписывать существующие файлы без подтверждения.
- Обрабатывать отсутствие прав, нехватку места и отмену.
- Записывать результат через временный файл в целевом каталоге с последующим безопасным завершением.
- При ошибке не оставлять частичный файл под именем готового экспорта.
- Логировать результат без содержимого финансовых данных.

### 11.2. Полный снимок SQLite

Для открытой БД использовать SQLite Online Backup API через `rusqlite` с feature `backup` либо другой проверенный механизм согласованного снимка.

**Запрещено копировать открытую БД обычным `std::fs::copy`.**

При WAL такой файл может не содержать подтверждённых изменений или оказаться несогласованным.

Снимок должен:

- соответствовать единому согласованному состоянию;
- включать завершённые до снимка транзакции;
- не включать частично выполненные операции;
- открываться как самостоятельная БД;
- проходить проверки целостности.

Имена файлов должны содержать временную метку и избегать коллизий.

### 11.3. ZIP

Если ZIP реализован:

- упаковывать готовый согласованный снимок, а не рабочий файл БД;
- включать манифест с версией приложения, фактической версией схемы и временем создания;
- при наличии checksum вычислять её по вложенному снимку;
- не выдавать checksum за шифрование или подтверждение подлинности.

Не зашивать `schema_version = 4`.

### 11.4. SQL-дамп

SQL-дамп должен восстанавливать пустую БД.

Включать:

- структуру таблиц;
- данные;
- необходимые индексы;
- триггеры;
- представления, если они существуют;
- историю миграций и сведения о версии схемы;
- состояние последовательностей, если оно влияет на продолжение идентификаторов.

Правила:

- корректно экранировать идентификаторы и значения;
- поддерживать `NULL`, Unicode, кавычки, переводы строк и BLOB;
- сохранять decimal-значения без преобразования во float;
- учитывать зависимости таблиц и самоссылочные категории;
- не вызывать повторно побочные эффекты триггеров при восстановлении данных;
- проверять восстановление в новую временную БД.

SQLite backup API создаёт бинарный снимок, а не SQL-текст. Не путать эти механизмы.

Не требовать установленной утилиты `sqlite3.exe` для обычного экспорта.

### 11.5. CSV и XLSX

- Использовать профильные библиотеки, а не ручное склеивание строк.
- Для CSV обеспечить UTF-8 и корректное экранирование.
- Политику BOM и разделителя определить с учётом Excel на Windows.
- Сохранять валюту, единицы измерения и понятные заголовки.
- Для XLSX использовать отдельные листы, когда это соответствует выбранному режиму.
- Недоверенный текст не должен исполняться как формула.

Для CSV учитывать formula injection в строках, начинающихся с `=`, `+`, `-`, `@` и управляющих символов. Защита текстового экспорта не должна изменять данные в БД и SQL-дампе.

Для XLSX записывать пользовательский текст именно как текст, а не как формулу.

Если XLSX-библиотека требует `f64`:

- преобразование допускается только на границе сериализации;
- финансовые расчёты до этого выполняются в `Decimal`;
- проверять ограничение точности Excel;
- при невозможности точного представления использовать текст или выдавать понятное предупреждение согласно принятой политике.

### 11.6. Импорт, если включён в задачу

- До восстановления создавать резервную копию текущей БД.
- Проверять целостность и совместимость схемы.
- Не заменять рабочую БД до завершения проверки.
- Закрывать активные соединения перед заменой.
- После восстановления проверять внешние ключи и историю миграций.
- При неудаче сохранять исходную рабочую БД.
- Для ZIP защищаться от path traversal, абсолютных путей, опасных ссылок и чрезмерного объёма распаковки.
- Не выполнять произвольный SQL из недоверенного файла без отдельного согласованного сценария.

## 12. Безопасность, логирование и производительность

### 12.1. Пользовательские данные

Не включать в репозиторий:

- рабочую БД пользователя;
- WAL/SHM-файлы;
- реальные резервные копии;
- реальные CSV/XLSX/SQL-экспорты;
- логи с персональными данными;
- пароли, ключи и локальные секреты.

Использовать синтетические fixtures.

Настраивать `.gitignore` адресно. Не исключать все `*.sql`, поскольку миграции должны храниться в Git.

Пароль запуска, SQLCipher и аудит изменений — необязательные функции. Не добавлять их без задания. Если шифрование требуется, не разрабатывать собственную криптографию и отдельно определить защиту резервных копий.

### 12.2. Логирование

Логировать:

- запуск и завершение приложения;
- применение миграций;
- технические ошибки;
- начало и результат экспорта;
- длительность значимых операций.

Не логировать без необходимости:

- комментарии операций;
- полные финансовые записи;
- содержимое выгрузок;
- пароли и ключи;
- SQL-параметры с пользовательскими данными.

Предусмотреть ротацию и ограничение объёма логов.

### 12.3. Производительность

- Создавать индексы под реальные фильтры и связи.
- Проверять запросы через `EXPLAIN QUERY PLAN`, когда это оправдано.
- Избегать N+1-запросов.
- Использовать виртуализацию таблиц или постраничную загрузку.
- Не пересчитывать весь отчёт при каждом событии UI.
- Для поиска применять debounce, если это необходимо.
- Не менять точную арифметику на float ради скорости.
- Не сортировать только текущую страницу, выдавая результат за сортировку полного набора.
- Измерять производительность в release-сборке на синтетическом наборе до 100 000 записей.

В отчёте об измерении указывать окружение, объём данных, сценарий и фактическое время. Не объявлять требование выполненным без измерения.

## 13. Проверки и тесты

Каждое изменение бизнес-логики сопровождается подходящими тестами. Исправление дефекта должно по возможности включать регрессионный тест.

### 13.1. Unit-тесты

Проверять:

- точность decimal-арифметики;
- округление и переполнение;
- валидацию денежных значений;
- сериализацию enum;
- валютную конвертацию и отсутствие курса;
- пустые выборки и нулевые итоги;
- границы периодов, недель и високосные даты;
- согласованные формулы прогнозов;
- иерархию категорий и обнаружение циклов.

### 13.2. Интеграционные тесты БД

Проверять:

- создание новой БД;
- повторный запуск без потери данных;
- обновление с поддерживаемых версий схемы;
- включение внешних ключей на каждом типе соединения;
- CRUD всех обязательных сущностей;
- защиту используемых банков и категорий;
- сохранение исторических неактивных категорий;
- уникальность связей;
- запрет связей разных банков;
- изменение банка карты и вклада при существующих связях;
- прямые SQL-изменения, обходящие прикладную валидацию;
- атомарный rollback при ошибке составной операции;
- явные ошибки при повреждённых decimal, датах и enum;
- отсутствие автоматического сброса повреждённой БД.

### 13.3. Тесты экспорта

Проверять:

- самостоятельное открытие DB-снимка;
- согласованность снимка при WAL;
- восстановление SQL-дампа в пустую БД;
- сохранение схемы, значений, связей и версии миграций;
- продолжение генерации идентификаторов после восстановления;
- кириллицу, кавычки, переносы строк и пустые значения;
- соответствие экспортируемого набора фильтрам;
- защиту табличного экспорта от формул;
- точность представления денег;
- ошибки записи, отмену и отсутствие ложного успеха;
- отсутствие перезаписи существующего файла без согласия.

Проверки восстановления в тестах обязательны для подтверждения качества дампа, даже если пользовательский импорт ещё не реализован.

### 13.4. UI и установка

Проверять:

- запуск на Windows 10/11 x64;
- доступность основных действий при 1280×720;
- русскоязычность интерфейса;
- валидацию форм;
- подтверждение удаления;
- отсутствие зависания при длительных операциях;
- сохранность данных после перезапуска;
- установку на чистой системе без отдельного Rust и SQLite;
- запуск без внешнего сервера и сетевого подключения.

Тесты не должны обращаться к реальному `%APPDATA%\FinanceApp`.

### 13.5. Команды качества

После создания workspace и `Cargo.lock` базовый набор:

```powershell
cargo fmt --all -- --check
cargo check --workspace --all-targets --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo build -p finance-app --release --locked
```

Для проверки Windows target при наличии соответствующего toolchain и linker:

```powershell
cargo build -p finance-app --release --locked --target x86_64-pc-windows-msvc
```

Не использовать `--all-features` автоматически, если features взаимоисключающие. Дополнительные конфигурации проверять отдельно.

Успешная сборка на Linux не доказывает работоспособность GUI и установщика на Windows.

Если команда не запускалась или завершилась ошибкой окружения, сообщи об этом явно.

## 15. Критерии завершения задачи

Задача считается завершённой, если:

- реализован именно запрошенный объём;
- поведение соответствует ТЗ и согласованным решениям;

- инварианты защищены вне интерфейса;
- ошибки не маскируются успешными результатами;
- пользовательские данные не подвергаются необоснованному риску;
- добавлены или обновлены подходящие тесты;
- выполнены доступные проверки;
- документация обновлена при изменении поведения или конфигурации;
- оставшиеся вопросы и ограничения перечислены явно;
- нет необъяснимых заглушек и фиктивной функциональности.

Не объявляй функцию полностью готовой, если её финансовая семантика ещё не согласована.

Не утверждай, что файл создан, тесты пройдены, Windows-сборка проверена или данные восстановлены, если соответствующее действие фактически не выполнено.
