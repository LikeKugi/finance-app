# Requirements

### Цель
Добавить к категории расходов булево состояние **«Регулярные расходы»** и использовать его в модуле «Анализ»: вместе с общим итогом расходов показывать отдельный итог по регулярным расходам.

### Функциональные требования
- Флаг доступен при создании и редактировании только категорий расходов; в категориях доходов поля нет.
- Подпись флага: «Регулярные расходы». По умолчанию значение `false` для новых и всех существующих категорий.
- Флаг персональный для конкретной категории: родитель не передаёт его дочерним категориям. Если отмечен ребёнок, его операции попадают в регулярные даже при неотмеченном родителе; если отмечен родитель, неотмеченные дети в регулярные не попадают.
- Историческая копия флага в транзакциях не нужна: изменение категории влияет на весь период отчёта.
- В Анализе для каждой валюты в таблицах расходов показываются две итоговые строки: существующий общий итог и новая «Итого в регулярных расходах» с количеством операций, суммой и долей от общего итога расходов в той же валюте.
- Если регулярных расходов нет, показывается `0`, `0.00`, `0%`; если расходов в валюте нет, итоговые строки не показываются.
- RUB и USD не складываются; все суммы и доли считаются в `Decimal`.

### Не входит
- Автоматическое создание повторяющихся операций, агрегация условий нескольких карт, прогнозы и начисление процентов.
- Фильтр «только регулярные» на страницах доходов/расходов.
- Отдельный срез регулярных расходов на круговой диаграмме: категории уже присутствуют в ней как обычные срезы, дополнительный срез привёл бы к двойному учёту.
- Изменение таблиц `incomes`, `expenses` и категорий доходов.

# Technical Design

### Текущая реализация
- `expense_categories` и `income_categories` созданы в `crates/db/migrations/V2__transactions_and_directories.sql`; у обеих есть `id`, `name`, `parent_id`, `is_active`. История миграций заканчивается V15.
- Список встроенных миграций задан константой `MIGRATIONS` в `crates/db/src/lib.rs`; перед обновлением распознанной старой БД создаётся консистентная резервная копия через `VACUUM INTO`.
- `Category` в `crates/core/src/lib.rs` — общая модель для доходов и расходов. `list_categories` и `save_category` в `crates/db/src/lib.rs` параметризуются `TransactionKind`.
- Форма категории и таблица справочника находятся в `crates/ui/src/gpui/directories.rs`; сейчас в форме есть только название, родитель и «Активна», а в таблице — «Название» и «Действия».
- `AnalysisTransaction`, `AnalysisCategoryTotal`, `AnalysisTotal`, `AnalysisSummary` и `summarize_analysis` находятся в `crates/core/src/lib.rs`. Итоговая строка таблицы формируется в `render_kind_summary` из `crates/ui/src/gpui/analysis.rs`.
- `load_analysis_transactions_with_filters` в `crates/db/src/lib.rs` читает операции через отдельное read-only соединение в одной транзакции и поддерживает рекурсивный фильтр категорий с потомками.

### Хранение и миграция
- Новая миграция `V16__expense_categories_regular.sql`: `ALTER TABLE expense_categories ADD COLUMN is_regular INTEGER NOT NULL DEFAULT 0 CHECK (is_regular IN (0, 1));`
- Существующие и новые строки получают `0`. `income_categories`, `expenses` и применённые миграции не меняются.
- V16 регистрируется в `MIGRATIONS`; простая `ALTER TABLE` не требует отключения внешних ключей, как пересборки V8/V15.
- В тестах, проверяющих резервную копию при обновлении до последней версии, префикс `data.before-migration-v15-` заменяется на `data.before-migration-v16-`. Production-код `backup_before_migration` уже подставляет `target_version` динамически.

### Доменная модель
- `Category.is_regular: Option<bool>`: `Some(...)` только для расходов, `None` для доходов. Это не позволяет случайно использовать флаг там, где его нет в БД.
- `AnalysisTransaction.is_regular: bool`: для расходов берётся из категории, для доходов всегда `false`.
- `AnalysisRegularTotal { amount: Decimal, transaction_count: usize, share_percent: Decimal }`.
- `AnalysisTotal.regular: Option<AnalysisRegularTotal>`: `Some` для расходов, включая нулевой результат; `None` для доходов.

### Расчёт отчёта
Для каждой валюты `R` — сумма расходов в категориях с `is_regular = true`, `N` — количество таких операций, `S = R / общий_итог_расходов_в_этой_валюте × 100`. Доля считается из точных сумм, округление до двух знаков — только при отображении. `summarize_analysis` использует `checked_add`, `checked_div` и `checked_mul`, не делит на ноль и при отсутствии регулярных операций создаёт нулевой `AnalysisRegularTotal`.

### Чтение операций
В `load_analysis_transactions_with_filters` SQL выбирает `c.is_regular AS is_regular` для расходов и `0 AS is_regular` для доходов. Имена таблиц по-прежнему берутся из whitelist `transaction_tables`. Рекурсивный фильтр категорий остаётся прежним: флаг читается из каждой конкретной строки-категории и не наследуется.

### Интерфейс
- `CategoryForm` получает состояние чекбокса; чекбокс показывается только для `TransactionKind::Expense`, новые категории расходов создаются с `false`.
- `save_category` получает `Some(checked)` для расходов и `None` для доходов; для доходов попытка записать флаг отклоняется или игнорируется согласно выбранному контракту — тихое появление бессмысленного значения недопустимо.
- Таблица категорий показывает признак отдельной текстовой колонкой «Регулярная» со значениями «Да» / «—» или суффиксом в названии; текст остаётся копируемым, цвет не является единственным носителем смысла.
- `AnalysisTable` получает `regular_total` из `AnalysisSummary`. В `render_kind_summary` под общим итогом расходов добавляется строка «Итого в регулярных расходах» с теми же четырьмя колонками. Для доходов строка не показывается. Первую строку для расходов можно подписать «Итого по расходам», для доходов сохранить «Итого».
- Длинную подпись после обрезки нужно сопроводить tooltip с полным текстом; ограничение 1280×720 сохраняется.

### Допущения
«Регулярные расходы» — классификационный признак категории, а не расписание платежей. Отсутствие исторической копии означает, что включение/выключение флага меняет прошедшие отчёты; это согласованное решение.

# Testing

### Проверки
- `finance-core`: регулярный итог суммирует только помеченные расходы; доходы с `is_regular = true` игнорируются; разделение по валютам; доля `R / общий_итог × 100`; ноль не вызывает деления на ноль; переполнение даёт `Overflow`; пустой summary обновлён под новую структуру.
- `finance-db`: новая БД V16 и обновление V1/V15 → V16 сохраняют категории, операции и историю миграций; `default = 0`; `CHECK` отклоняет значения вне `0/1`; `save_category` → `list_categories` roundtrip; `load_analysis_transactions` читает флаг у расходов и `false` у доходов.
- `finance-db`: category filter с потомками проверяет оба направления наследования: отмеченный родитель с неотмеченным ребёнком и неотмеченный родитель с отмеченным ребёнком; даты, валюта и category filter одинаково влияют на общий и регулярный итоги; повреждённый decimal по-прежнему приводит к ошибке.
- `finance-ui`: чекбокс только у расходов, сохранение флага, отображение в таблице категорий; `AnalysisTable::set_summary` извлекает regular total; строка «Итого в регулярных расходах» появляется только для Expense; при нуле показывается `0%`; pie chart не получает отдельный regular-срез.
- Запустить `cargo fmt --all -- --check`, `cargo check --workspace --all-targets --locked`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --workspace --locked`, `cargo build -p finance-app --release --locked`.
- Windows 10/11 x64 и 1280×720 отметить как непроверенные в текущем окружении; отдельная Windows-сборка и ручная проверка требуются отдельно.
